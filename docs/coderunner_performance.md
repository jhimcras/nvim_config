# coderunner 파싱·저장 검사 성능

2026-10-30, Linux 6.1.177-3-MANJARO, Neovim 0.12.4/LuaJIT에서 측정했다.
5,000줄, ID가 있는 dot 블록 200개, 블록마다 코드 1줄과 일반 문단 22줄이다.
콜드 조회는 1회, 캐시 조회는 1,000회, 나머지는 30회 평균이다.
프로세스 실행과 이미지 디코딩은 포함하지 않는다.

| 시나리오 | 최초 측정 ms/회 | 개선 후 ms/회 | 개선 후 파싱 / 전체 버퍼 읽기 |
| --- | ---: | ---: | --- |
| 첫 `blocks.get` | 92.240 | 55.614 | 1 / 1 |
| 변경 없는 `blocks.get` | 0.001074 | 0.001223 | 0 / 0 (1,000회 합계) |
| 매번 문단 편집 후 `blocks.get` | 92.334 | 57.472 | 30 / 30 |
| 디스크 내용·설정이 같은 저장 검사 | 114.849 | 0.100404 | 0 / 0 (30회 합계) |
| 매번 한 블록의 저장 키 변경 | 114.566 | 79.669 | 30 / 0 |

changedtick 캐시는 같은 버퍼의 반복 파싱과 전체 읽기를 피한다. 끝 개행 옵션 변경도
캐시를 무효화한다. 저장 검사는 디스크를 다시 읽되 내용·경로·설정·신뢰 상태가 같으면
이미 계산한 블록과 키를 재사용한다. 이미지 표식이 없는 인접 문단은 inline 파서를 만들지 않는다.
신뢰 변경 후 같은 문서를 저장하면 허용 판정과 키를 다시 수집한다는 회귀 스펙을 추가했다.

변경 없는 저장 검사는 약 0.1ms다. 처음과 편집 후에는 여전히 전체 문서 파싱이 필요하며,
이 입력에서 56–80ms가 걸린다. 큰 문서의 편집·변경 저장 비용까지 사라졌다는 의미는 아니다.
렌더 디바운스는 1시간으로 설정해 검사 자체만 측정했고, 모든 시나리오의 외부 프로세스 수는 0이다.
변경 저장 수치에는 테스트용 디스크 쓰기도 포함된다. 실행 후 예약은 취소하고 임시 문서를 삭제한다.

재현:

```sh
bench_runtime=$(mktemp -d)
XDG_CACHE_HOME="$bench_runtime/cache" XDG_STATE_HOME="$bench_runtime/state" \
  NVIM_LOG_FILE="$bench_runtime/nvim.log" \
  nvim --headless -u NONE -i NONE -l tests/manual/benchmark_coderunner.lua
rm -rf "$bench_runtime"
```

스크립트는 시나리오별 JSON에 호출 수, ms/회, 파싱·버퍼 읽기·프로세스 수를 출력한다.
이 결과는 headless 검사 비용이며 실제 GUI 렌더링 지연이나 다른 플랫폼의 수치를 보장하지 않는다.
